# Delta Lake: Advanced Table Features

The table features beyond reading, writing and maintaining a table (see [Delta Lake & Modern Lakehouse Storage](/articles/delta)): identity columns and row tracking, liquid clustering, column changes, dropping table features, and variant columns. Each follows delta-spark 4.4 (Spark 4.2), and tables Spark or Databricks created with these features are read and written as Spark reads and writes them (variant tables are read only). What is not supported yet is listed in [Compatibility & Known Limitations](/articles/delta-limitations).

---

## 1. Identity Columns & Row Tracking

`Delta.CreateTable` creates an empty table, as Spark's `CREATE TABLE`: schema, partition columns, table properties and identity columns. An identity column is an `Int64` column whose values writes generate, `start`, `start + step`, … after the highest value given so far. With `generatedAlways` (the default) writes may not bring values for it; otherwise (GENERATED BY DEFAULT) rows that bring a value keep it. Identity columns are never updated.

With `DeltaTableProperties.EnableRowTracking`, every row keeps a stable row id through updates, merges and optimize; `ScanDelta` / `ReadDelta` return it, and the version that last changed the row, under the names given (Spark's `_metadata.row_id` and `_metadata.row_commit_version`). Set on an existing table, the property gives the rows already there their ids.

`DeltaTableProperties.RowTrackingSuspended` stops giving ids to new files, as Spark's `delta.rowTrackingSuspended`; it cannot be true while row tracking is on, so set `EnableRowTracking` to false in the same `SetTableProperties` call. Setting it back to false (with `EnableRowTracking` true in the same call, if wanted) resumes the ids after the highest one given, and gives the files written meanwhile theirs.

::: code-group

```csharp [C# (Fluent)]
Delta.CreateTable(
    "./lake/orders",
    PolarsSchema.From<Order>(),
    properties: new() { [DeltaTableProperties.EnableRowTracking] = "true" },
    identityColumns: [new DeltaIdentityColumn("OrderId", Start: 1000, Step: 1)]);

// OrderId is generated: 1000, 1001, ...
using var items = DataFrame.From<NewItem>([new("pen"), new("ink")]);
items.WriteDelta("./lake/orders", mode: DeltaSaveMode.Append);

var withIds = DataFrame.ReadDelta("./lake/orders", rowIdColumn: "row_id", rowCommitVersionColumn: "row_version");

record Order(long OrderId, string Item);
record NewItem(string Item);
```

```fsharp [F# (Pipeline)]
Delta.CreateTable(
    "./lake/orders",
    PolarsSchema([ "order_id", DataType.Int64; "item", DataType.String ]),
    properties = [ DeltaTableProperties.EnableRowTracking, "true" ],
    identityColumns = [ DeltaIdentityColumn("order_id", start = 1000L) ])

let items = DataFrame.create [| Series.create("item", [ "pen"; "ink" ]) |]
items.WriteDelta("./lake/orders", mode = DeltaSaveMode.Append)

let withIds = DataFrame.ReadDelta("./lake/orders", rowIdColumn = "row_id", rowCommitVersionColumn = "row_version")
```

:::

## 2. Liquid Clustering

Liquid clustering (Spark's `CLUSTER BY`) lays out a table's data by up to four clustering columns, so that filters on any of them skip files, without partitioning the table. `Delta.CreateTable` (or a write that creates the table) takes the columns; `Delta.Optimize` then clusters the data: rows are cut into ranges of a Hilbert curve over the columns, each range written to its own files. Appends, updates, deletes and merges write unclustered files, as Spark's do; the next optimize clusters them, merging them with the small clustered cubes. `Delta.ClusterBy` changes the columns (none to stop clustering); data already clustered keeps its layout until an optimize with `full`. Tables Spark or Databricks clustered are read, written and optimized the same way, and Spark recognizes the files clustered here.

Clustering columns must be of a type with statistics (numbers, strings, dates, timestamps, decimals) and among the columns that get them (`delta.dataSkippingNumIndexedCols`, `delta.dataSkippingStatsColumns`); a clustered table cannot be partitioned, and Z-ordering does not apply to it.

::: code-group

```csharp [C# (Fluent)]
Delta.CreateTable("./lake/events", PolarsSchema.From<Event>(), clusterBy: ["User", "Ts"]);

events.WriteDelta("./lake/events", mode: DeltaSaveMode.Append);
Delta.Optimize("./lake/events");                  // clusters the new data

Delta.ClusterBy("./lake/events", ["Kind"]);       // new clustering columns
Delta.Optimize("./lake/events", full: true);      // reclusters the data clustered by the old ones

record Event(DateTime Ts, string User, string Kind);
```

```fsharp [F# (Pipeline)]
Delta.CreateTable(
    "./lake/events",
    PolarsSchema([ "ts", DataType.Datetime(TimeUnit.Microseconds); "user", DataType.String; "kind", DataType.String ]),
    clusterBy = [ "user"; "ts" ])

events.WriteDelta("./lake/events", mode = DeltaSaveMode.Append)
Delta.Optimize("./lake/events") |> ignore

Delta.ClusterBy("./lake/events", [ "kind" ])
Delta.Optimize("./lake/events", full = true) |> ignore
```

:::

## 3. Column Changes

Columns are renamed, dropped and widened as Spark's `ALTER TABLE` does it: one commit that changes the schema, without rewriting data. Nested fields are named with dots, `element` for an array's element and `key` / `value` for a map's (`items.element.price`); a part holding a dot goes in backticks.

* `Delta.RenameColumn` and `Delta.DropColumns` need column mapping (`delta.columnMapping.mode` = `name`, which `Delta.SetTableProperties` turns on for an existing table without rewriting it): data files keep their physical column names, so a renamed column reads its old data, and a dropped one is no longer read (a column added later under the same name is a new, empty column). Partition columns and `delta.dataSkippingStatsColumns` follow a rename. Partition columns, clustering columns (and structs holding one) and the last column of the table or of a struct cannot be dropped.
* `Delta.ChangeColumnType` needs type widening (`delta.enableTypeWidening` = `true`). Allowed: integers to wider integers, a wide enough decimal, or (from Int8, Int16, Int32) Float64; Float32 to Float64; decimals to wider decimals; Date to Datetime without a time zone (needs the `timestampNtz` feature). Older files are read in their own types and cast.

::: code-group

```csharp [C# (Fluent)]
Delta.SetTableProperties("./lake/orders", new() { ["delta.columnMapping.mode"] = "name", ["delta.enableTypeWidening"] = "true" });

Delta.RenameColumn("./lake/orders", "customer", "client");
Delta.RenameColumn("./lake/orders", "address.zip", "postcode");      // a nested field
Delta.DropColumns("./lake/orders", ["comment", "address.line2"]);
Delta.ChangeColumnType("./lake/orders", "quantity", DataType.Int64);  // Int32 → Int64
```

```fsharp [F# (Pipeline)]
Delta.SetTableProperties("./lake/orders", [ "delta.columnMapping.mode", "name"; "delta.enableTypeWidening", "true" ])

Delta.RenameColumn("./lake/orders", "customer", "client")
Delta.RenameColumn("./lake/orders", "address.zip", "postcode")
Delta.DropColumns("./lake/orders", [ "comment"; "address.line2" ])
Delta.ChangeColumnType("./lake/orders", "quantity", DataType.Int64)
```

:::

## 4. Dropping Table Features

`Delta.DropFeature` removes a table feature, as Spark's `ALTER TABLE … DROP FEATURE` does, so readers and writers that lack the feature can use the table again. The feature's traces go first, each step its own commit and each skipped when already done, so a drop that was interrupted is finished by running it again:

* **Deletion vectors:** the property is turned off, the files with deletion vectors are rewritten without the deleted rows (`REORG … APPLY (PURGE)`), and the vector files are recorded for vacuum.
* **Type widening:** the property is turned off, the files that still hold a column in an older type (found from their Parquet footers) are rewritten in the table's types, and the type changes leave the schema.
* **Column mapping:** every file is rewritten with the columns under their logical names (deleted rows left out), in one commit that also takes the mapping out of the schema. Column names that a Parquet file cannot hold without column mapping (with any of ` ,;{}()\n\t=`) are refused: rename them first.
* **Row tracking:** tracking is suspended and turned off, then the row ids leave the log.
* **In-commit timestamps, V2 checkpoints:** the properties are turned off.
* **Check constraints, domain metadata:** refused while the table still has constraints or domains.

Row ids are kept through every rewrite. A reader feature (`deletionVectors`, `typeWidening`, `columnMapping`, `v2Checkpoint`, `vacuumProtocolCheck`) then leaves the protocol behind three empty commits with checkpoints, under the `checkpointProtection` writer feature: readers start at those checkpoints and never need the older commits, so the table is readable without the feature at once, and log cleanup keeps the history before the drop until it can all go together. A writer feature (`inCommitTimestamp`, `rowTracking`, `domainMetadata`, `checkConstraints`) leaves in one commit. Unity Catalog tables take `UnityCatalog.DropFeature(catalog, schema, table, feature)`. `appendOnly`, `invariants`, `changeDataFeed`, `generatedColumns`, `identityColumns`, `timestampNtz`, `clustering` and `checkpointProtection` cannot be dropped, nor can a feature another feature depends on (`domainMetadata` under row tracking or clustering).

::: code-group

```csharp [C# (Fluent)]
Delta.DropFeature("./lake/orders", DeltaTableFeatures.DeletionVectors);
Delta.DropFeature("./lake/orders", DeltaTableFeatures.ColumnMapping);
Delta.DropFeature("./lake/orders", "typeWidening");
```

```fsharp [F# (Pipeline)]
Delta.DropFeature("./lake/orders", DeltaTableFeatures.DeletionVectors)
Delta.DropFeature("./lake/orders", DeltaTableFeatures.ColumnMapping)
Delta.DropFeature("./lake/orders", "typeWidening")
```

:::

## 5. Variant Columns

Tables with `VARIANT` columns (Spark 4 and Databricks semi-structured data, the `variantType` feature) are read, at any depth: top-level columns, struct fields, array elements and map values. A variant is read as it is stored, a struct of its `value` and `metadata` binaries (the Parquet Variant encoding), or, with `variantAsJson: true`, as JSON text, exactly as Spark's `to_json` renders it (timestamps in UTC). Such tables are read only.

The Polars engine cannot open these files yet, so Polars.NET reads them through a patch of its own: every file a scan selects is read whole into memory when the scan is created. See [Compatibility & Known Limitations](/articles/delta-limitations) for what that costs.

::: code-group

```csharp [C# (Fluent)]
using var raw = DataFrame.ReadDelta("./lake/events");                        // payload: struct{value, metadata}
using var json = DataFrame.ReadDelta("./lake/events", variantAsJson: true);  // payload: String

using var clicks = json
    .Filter(Col("payload").Str.JsonPathMatch("$.kind") == "click")
    .Select(Col("id"), Col("payload"));
```

```fsharp [F# (Pipeline)]
let raw = DataFrame.ReadDelta("./lake/events")                       // payload: struct{value, metadata}
let json = DataFrame.ReadDelta("./lake/events", variantAsJson = true) // payload: String
```

:::

## 6. Catalog-Managed Tables

A catalog-managed table (the `catalogManaged` feature, which Unity Catalog's managed Delta tables use) is committed to through its catalog rather than by writing log files: a writer stages a commit, the catalog ratifies it as the next version, and the commit is then published to `_delta_log`. The catalog is the authority on the table's latest version, which may include commits not published yet.

Polars.NET reads and writes such tables through `UnityCatalog`, as Delta Spark 4.4 does with the Unity Catalog connector: scans see every commit the catalog ratified, and appends, deletes, merges, schema evolution, `ClusterCatalogTable`, `DropCatalogColumns`, `ChangeCatalogColumnType`, properties and `DeltaRestore` commit through it. The catalog keeps a copy of the table's properties, columns, protocol and clustering, and each commit updates it. Commits other writers left unpublished are published first, in order.

The same table cannot be read or written by its path: the catalog may know of commits the files do not show yet. Operations Delta Spark refuses on these tables are refused here too: `OptimizeCatalogTable`, `DeltaVacuum`, `RenameCatalogColumn` and `DropFeature`. Log cleanup is left to the catalog.

::: code-group

```csharp [C# (Fluent)]
using var uc = new UnityCatalog("https://my-workspace.cloud.databricks.com", token);

using var events = uc.ScanCatalogTable("main", "sales", "events").Collect();

using var more = DataFrame.From<Event>([new(7, "click")]);
more.Lazy().SinkCatalogTable(uc, "main", "sales", "events");
uc.DeleteCatalogRecords("main", "sales", "events", Col("id") == 3);

record Event(long id, string kind);
```

```fsharp [F# (Pipeline)]
use uc = new UnityCatalog("https://my-workspace.cloud.databricks.com", token)

let events = uc.ScanCatalogTable("main", "sales", "events").Collect()
uc.DeleteCatalogRecords("main", "sales", "events", pl.col "id" .== pl.lit 3L)
```

:::

Creating catalog-managed tables is not supported yet: create them with Spark or Databricks, then use them here.
